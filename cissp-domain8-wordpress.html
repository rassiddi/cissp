System Development Life Cycle (SDLC)
Security should be "baked in, not bolted on." The cost to fix a defect EXPONENTIALLY INCREASES at each stage of the SDLC. A flaw caught in design costs ~10× less than one caught in production. Security must be integrated at EVERY phase — not added at the end.
Phase 1
Project initiation
Feasibility, cost, risk analysis. Management approval. Define basic security objectives. Conceptual definition.
Phase 2
Functional analysis
Define needs and requirements. Review proposed security controls. Functional requirements definition.
Phase 3
System design
Develop detailed design specs. Examine security controls. Control specifications development and design review.
Phase 4
Development
Programmers write code. Unit testing, prototyping, verification, validation. Code review and security testing.
Phase 5
Acceptance & implementation
Separation of duties, security testing, data validation, bounds checking, certification, accreditation. Release control.
Phase 6
Operations & maintenance
Production release, cert/accreditation. Ongoing patching, monitoring, change management.
Phase 7
Revisions / disposal
Remove from service. Sanitisation and destruction of unneeded data. Data migration to new system.
Software CMM — Capability Maturity Model
Quality of software is a DIRECT function of the quality of the development and maintenance process. Defined by Carnegie Mellon University SEI. Levels 1–2 = REACTIVE. Levels 3–5 = PROACTIVE. Biggest jump in maturity = Level 2 → 3 (reactive to proactive).
LevelNameKey characteristic
1 — ReactiveInitial / Ad-hocCompetent people, informal processes. Absence of formal process. Success depends on individual effort.
2 — ReactiveRepeatableProject management processes established. Basic lifecycle management. Can repeat previous successes.
3 — ProactiveDefinedEngineering processes, basic lifecycle management, code reuse, requirements management, QA, configuration management.
4 — ProactiveManagedProduct and process improvement. Quantitatively controlled — metrics-driven decisions.
5 — ProactiveOptimisingContinuous process improvement. Organisation learns from data and continuously improves.
SDLC security activities by phase — tap to expand
Requirements phase security
Define security requirements: CIA requirements, regulatory compliance, data classification. Identify threat model. Define security architecture. Misuse case analysis — what could go wrong? Define authentication, authorisation, audit requirements. Security requirements must be MEASURABLE.
Design phase security
Threat modelling (STRIDE/DREAD). Secure design principles: least privilege, defence in depth, fail-safe. Architecture review. Choose appropriate security frameworks. Design peer review — structured walk-through. Design review is most cost-effective point to find security flaws.
Development phase security
Secure coding standards and guidelines. Code review (peer review / Fagan inspection). SAST — static application security testing. Input validation implemented. Avoid dangerous functions (strcpy, gets). Secrets management — no hardcoded credentials. Unit testing with security test cases.
Testing phase security
DAST — dynamic application security testing. Penetration testing. Vulnerability scanning. Regression testing — new code doesn't break old security controls. User acceptance testing (UAT). Certification — technical evaluation of security features. OWASP ZAP, Burp Suite for web apps.
Deployment phase security
Accreditation — formal management acceptance. Change control process. Production deployment checklist. Security configuration baseline applied. Separation of duties in production release. Developer should NOT deploy to production (conflict of interest). Rollback plan in place.
Maintenance phase security
Patch management — timely application of security patches. Continuous monitoring. Log review for anomalies. Configuration management — track all changes. Periodic security reassessment. Whenever a change happens, recertification is required.
Software development methodologies
Waterfall
Sequential
Each phase completed before next begins. Can go back only ONE step. Simple but assumes a phase ends at a specific time — rigid. System Requirements → Software Requirements → Analysis → Program Design → Coding → Testing → Operations. Includes V&V (Verification = doing it right, Validation = doing the right thing).
Spiral
Risk-driven iterative
Angular axis = progress made. Radial axis = cost. Iterative cycles through: planning → risk analysis → engineering → evaluation. Each cycle produces a prototype. Risk assessment at each iteration. Best for large, complex, high-risk projects. Combines waterfall discipline with iterative flexibility.
Agile
Iterative · customer-focused
Individuals and interactions over processes and tools. Working software over comprehensive documentation. Customer collaboration over contract negotiation. Responding to change over following a plan. Working software is PRIMARY measure of success. Short sprints (1–4 weeks). Continuous customer feedback.
Cleanroom
Quality-first
Write code correctly the FIRST TIME — quality through design. Prove original design before coding. Formal mathematical verification of design. Statistical testing rather than debugging. Zero-defect mindset. Used for safety-critical systems.
Prototype
Customer view
Customer view taken into account from the start. Working prototype built rapidly to validate requirements. PROTOTYPING = customer view. Helps discover requirements that weren't explicit. Risk: prototype becomes production code without proper security review.
RAD — Rapid Application Development
Speed-focused
Heavy use of tools and reuse. Less emphasis on planning. Faster delivery. Risk: security may be deprioritised for speed. Requires highly skilled development team. Iterative with continuous user involvement.

Project management tools
Gantt chart
Bar chart showing interrelationships over time between projects and schedules. Provides graphical illustration of a schedule. Helps plan, coordinate, and track specific tasks. Shows task dependencies and durations. WBS (Work Breakdown Structure) is a subpart of Gantt.
PERT chart
Program Evaluation and Review Technique. Used to judge size of software product in development and calculate standard deviation for risk assessment. Relates: lowest possible size, most likely size, and highest possible size of each component. Directs improvements to project management and software coding.
Compiler vs interpreter
Compiler: translates entire higher-level program into an executable file before running. Interpreter: reads and executes higher-level code ONE LINE AT A TIME — slower but easier to debug. JavaScript = interpreted. Java, C, C++ = compiled. Compiled code is HARDER to analyse for malicious content.
OWASP Top 10 — most critical web app security risks
OWASP (Open Web Application Security Project) is the most authoritative source on web application security issues. The Top 10 represents the most critical risks — exam frequently tests these. OWASP ZAP and Burp Suite are the standard testing tools.
A01
Broken Access Control
Users can act outside their intended permissions. Includes IDOR (Insecure Direct Object References), privilege escalation, CORS misconfigurations. Prevention: deny by default, server-side enforcement.
A02
Cryptographic Failures
Sensitive data exposed due to weak/missing encryption. Weak algorithms (MD5, SHA-1, DES), data in cleartext, improper key management. Prevention: use strong algorithms (AES-256, SHA-256+), TLS everywhere.
A03
Injection
SQL, NoSQL, OS, LDAP injection — untrusted data sent to interpreter. SQL injection: attacker manipulates database queries. Prevention: parameterised queries, bind variables, input validation, stored procedures.
A04
Insecure Design
Missing or ineffective security controls at design stage. Cannot fix poor design with implementation controls alone. Prevention: threat modelling, secure design patterns, security requirements in design phase.
A05
Security Misconfiguration
Default credentials, unnecessary features enabled, unpatched systems, verbose error messages. Most commonly found vulnerability. Prevention: hardening guides, remove defaults, automated configuration checking.
A06
Vulnerable Components
Using components with known vulnerabilities — libraries, frameworks, modules. Prevention: inventory all components, check NVD/CVE, update regularly, remove unused components.
A07
Auth & Identification Failures
Broken authentication — weak passwords, credential stuffing, session fixation, missing MFA. Prevention: MFA, strong passwords, secure session management, lockout policies.
A08
Software & Data Integrity Failures
Code and infrastructure not protected against integrity violations. Includes insecure deserialization, auto-update without verification. Prevention: digital signatures, hash verification, CI/CD pipeline integrity.
A09
Security Logging Failures
Insufficient logging and monitoring — attacks undetected. Without logs, breaches go unnoticed for months. Prevention: log all auth events, access controls, input validation failures. Centralise in SIEM.
A10
Server-Side Request Forgery (SSRF)
Application fetches remote resource using attacker-supplied URL — bypasses firewall, VPN, ACLs. Allows access to internal services. Prevention: validate and sanitise all user-supplied URLs, network-layer controls.
Common web application attacks
SQL Injection
Directly attacks a database through a web application. Classic example: ' OR '1'='1 or using semicolon to escape. CARROT technique: comment out remainder of query. Prevention: parameterised queries/prepared statements, bind variables, stored procedures, input validation. ORM frameworks help but are not foolproof.
Cross-Site Scripting (XSS)
Uses reflected input to trick a user's browser into executing untrusted code from a trusted site. Stored XSS: malicious script saved in database. Reflected XSS: script in URL/input reflected back. DOM-based XSS: client-side script manipulation. Prevention: output encoding, Content Security Policy (CSP), input validation.
CSRF — Cross-Site Request Forgery
Attacks exploit the trust that sites have in a user's browser by forcing submission of authenticated requests to third-party sites. Differs from XSS: XSS exploits trust in a site; CSRF exploits trust in user's browser. Prevention: anti-CSRF tokens, SameSite cookie attribute, re-authentication for sensitive actions.
Buffer overflow
Writing more data to a buffer than it can hold — overwrites adjacent memory including return address. Can redirect execution to attacker's code. Prevention: bounds checking, input validation, safe string functions, ASLR (Address Space Layout Randomisation), DEP (Data Execution Prevention), stack canaries.
Directory traversal
Attacker manipulates file path input to navigate up the directory tree and access files outside the web root. Example: %252E%252Fetc/passwd (%252E = dot, %252F = slash). Prevention: validate and sanitise file paths, use chroot jails, whitelist allowed directories.
Race condition / TOC-TOU
Time of Check to Time of Use — window between when a condition is checked and when it is used. Attacker changes state in that window. Prevention: atomic operations, file locking, transactions with proper isolation. Common in file permission checks and authentication flows.
Input validation
ONLY way to eliminate buffer overflows is proper data validation. Validate: type, length, format, range. Whitelist approach (allow only known good) is stronger than blacklist. Server-side validation is mandatory — client-side only is never sufficient. Bind variables in SQL = best practice for DB input.
API key security
API keys are like passwords — must be treated as very sensitive information. Never hardcode API keys in source code. Store in secure locations (secrets manager). Transmit only over encrypted channels (HTTPS). If API key compromised, attacker can interact as legitimate user. Rotate regularly, limit scope.
Secure coding principles
Defence in depth in code
Multiple layers of security controls — if one fails, others remain. Input validation + parameterised queries + WAF + network controls. Never rely on a single control. Error messages must not reveal internal details (stack traces, SQL errors). Fail securely — deny by default.
Least privilege in code
Application should run with minimum permissions needed. Database connections should use accounts with only required permissions (no DBA access for web app). Application accounts should not be admin. Service accounts: minimal necessary privileges. Limit what compromised code can do.
Credential management
Never store passwords in plaintext — always hash with salt (bcrypt, PBKDF2, Argon2). Separate credential storage from application code. Use secrets managers (HashiCorp Vault, AWS Secrets Manager). Rotate credentials regularly. API keys and database passwords treated as secrets.
Error handling
Never expose internal details in error messages — no stack traces, SQL errors, or file paths visible to users. Log errors internally with full detail. Return generic error messages to users. Fail securely — system should be in known secure state after an error. Error handling should not create security bypass opportunities.
Database concepts — ACID model
ACID = Atomicity, Consistency, Isolation, Durability. These four properties ensure database transactions are processed reliably and protect data integrity even in failure scenarios.
Atomicity
All-or-nothing
Transaction completes entirely or is rolled back completely. No partial transactions. If any part fails, entire transaction is rolled back as if it never occurred.
Consistency
Valid state only
All transactions begin and end in a consistent state — all database rules maintained. No other transaction can use inconsistent intermediate data.
Isolation
Transactions separate
Transactions operate independently. If two transactions modify same data, one must complete before the other can start. Prevents dirty reads and lost updates.
Durability
Committed = permanent
Once committed, transactions are preserved even through system failure. Ensured through transaction logs, journaling, and backup mechanisms.
Database structure terminology
Tuple
Row / Record
A single entry in a relational database table. Also called a record.
Attribute
Column / Field
A characteristic of an entity. Degree of DB = number of attributes (columns).
Primary key
Unique row identifier
Cannot be null, cannot change. Uniquely identifies each record. Only one per table.
Foreign key
Reference to another table
Links tables together. Enforces referential integrity. Must reference a valid primary key.
Candidate key
Potential primary key
Any attribute that could uniquely identify a record. One is chosen as primary key; others are alternate keys.
View
Virtual table
Content-dependent access control. Retrieves specific columns from one or more tables. Does not store data — queries on access.
DDL
Data Definition Language
Defines structure and schema — CREATE, ALTER, DROP tables.
DML
Data Manipulation Language
Manipulates data — SELECT, INSERT, UPDATE, DELETE. SQL SUDIGR: Select, Update, Delete, Insert, Grant, Revoke.
DCL
Data Control Language
Controls access — GRANT and REVOKE statements. Manages database permissions.
Database security threats
Aggregation attack
Combining multiple pieces of non-sensitive information to create something of higher sensitivity or value. SQL aggregate functions (SUM, COUNT, AVG) combine data. Prevention: restrict query capabilities, limit what aggregate queries can return, access controls on combined queries. Also called privilege creep in IAM context.
Inference attack
Gaining access to higher-classification information through logical deduction from lower-level data. Uses human deductive reasoning rather than raw mathematical ability. Countermeasure: polyinstantiation — providing different data to users of different clearance levels for the same primary key. Makes inference impossible.
Database contamination
Mixing data with different classification levels or need-to-know requirements. Significant security challenge in multilevel databases. Solution: deploy trusted front end to add multilevel security to legacy DBMS. Database partitioning splits database by security level.
Concurrency issues
Dirty reads: reading uncommitted data written by another transaction. Lost updates: one transaction overwrites another's data. Incorrect summaries: aggregate function running during modification produces wrong results. Prevention: proper transaction isolation levels (serialisable is strictest), database locking mechanisms.
Data warehousing & mining
Data warehouse: large database storing data from multiple sources for analysis. Data mining: analysing warehouse data for patterns and correlations. Security concern: mining can reveal sensitive patterns not visible in individual records (aggregation risk). Metadata stored in a more secure container called a Data Mart.
Object-relational mapping (ORM)
ODBC (Open Database Connectivity): allows applications to communicate with different database types without being directly programmed for each. Acts as a proxy. ORMs (Object Relational Mappers) map database tables to code objects — can prevent SQL injection if used correctly. Must still be configured securely.
Malware types — complete reference
Virus
Reproduces using a HOST application — inserts/attaches itself to the file. Requires user action to spread. Types: Boot sector (overwrites boot record), System infector (infects OS files), Companion (stores in separate file), Stealth (hides modifications), Polymorphic (changes garble pattern each spread — hard to detect), Multipart (infects both boot and executables), Macro virus (Word/VBA — most common in office docs), Memory resident. Antivirus: Signature-based (cannot detect new malware). Heuristic/behavioural (CAN detect new malware).
Worm
Reproduces ON ITS OWN without a host application. Self-propagating — spreads across networks automatically. Capacity to propagate independent of user action. Can consume enormous bandwidth. Famous example: Stuxnet = worm targeting Iranian nuclear capability (SCADA/PLC rootkit). Morris Worm = first internet worm (1988).
Trojan horse
Program DISGUISED as a useful/legitimate program/tool. Pretends to do one thing while performing another. Does NOT self-replicate. RAT (Remote Access Trojan): remote control program that allows unauthorised remote access (Back Orifice, Sub7, NetBus). Users must be tricked into running it.
Logic bomb
Executes when a certain event happens (like accessing a bank account, employee being fired) or a specific date/time occurs. Triggered by condition — dormant until trigger. Example: "Execute on April 1, 2025." Often planted by disgruntled insiders. Very difficult to detect when dormant.
Ransomware
Encrypts victim's files and demands ransom for decryption key. Attacks availability primarily. Spreads like worm or through phishing. Prevention: regular offline backups (not connected to network), patching, email filtering, user training. NEVER guaranteed that paying ransom restores access.
Rootkit
Malware that achieves deep-level access and hides itself and other malware from the OS. Operates at kernel level (Ring 0) — extremely difficult to detect and remove. May require complete OS reinstall. UEFI rootkits persist across OS reinstalls. Stuxnet contained a rootkit component.
Botnet / zombie
Network of compromised systems running zombie code. Command and control (C&C) server directs bots. Used for: DDoS attacks, spam campaigns, credential stuffing, cryptomining, click fraud. Botnet operators rent access to botnets. Individual bots may not show obvious signs of infection.
Spyware / adware
Spyware: secretly monitors user activity — keyloggers, screen capture, browser history. Often bundled with legitimate software. Adware: displays unwanted advertisements. Some adware also functions as spyware. Prevention: anti-spyware tools, browser protection, careful software installation.
Drive-by download
Malware installs itself without user's knowledge when visiting a website. Takes advantage of vulnerabilities in browser or browser plug-ins (Java, Flash, PDF reader). No user interaction required beyond visiting the page. Prevention: keep browsers and plugins patched, use NoScript, disable unnecessary plugins.
Phlashing attack
Malicious variation of official BIOS or firmware update that introduces remote control or other malicious features. Permanently damages the device (PDoS — Permanent Denial of Service). UEFI is the modern replacement for BIOS. Firmware version control = manual updates from trusted sources only.
Malware defence strategies
Signature-based AV
Compares files against a database of known malware signatures (hashes, byte sequences). Fast and accurate for KNOWN malware. CANNOT detect new or zero-day malware — signature must exist first. Requires constant updates. Polymorphic viruses can evade by changing their signature.
Heuristic / behavioural AV
Analyses behaviour and characteristics rather than signatures. CAN detect new/unknown malware. May produce false positives. Sandboxing: runs suspicious code in isolated environment to observe behaviour. More resource-intensive than signature scanning. Used together with signature-based for best protection.
Application whitelisting
Only authorised applications can be installed or run. Strongest defence against malware — if it's not on the whitelist, it cannot execute. High administrative overhead. Effective in controlled environments (ATMs, SCADA). Mobile: app store controls = form of whitelisting.
DevSecOps — integrating security into DevOps
DevOps = Development + Operations. DevSecOps = Development + Security + Operations. Security must be shifted LEFT — integrated early in the development process rather than being a gate at the end. Working software is the primary measure of success in Agile/DevOps.
DevOps principles
Integrates: Software Development, Quality Assurance, IT Operations. Note: DevOps as originally defined does NOT include Security — DevSecOps explicitly adds it. Continuous Integration (CI): developers merge code frequently. Continuous Delivery (CD): code always in deployable state. Continuous Deployment: automatic deployment to production.
Security in CI/CD pipeline
SAST: static analysis on every code commit (shift-left). Dependency scanning: check third-party libraries for vulnerabilities. Secret scanning: prevent credentials committed to code repo. DAST: automated testing of running application. Container scanning: check Docker images for vulnerabilities. Infrastructure as Code (IaC) security scanning.
Separation of environments
Development → Testing/QA → Staging → Production. DEVELOPERS MUST NOT HAVE ACCESS TO PRODUCTION (separation of duties). Each environment should have appropriate security controls. Production data should NEVER be used in development/testing (use anonymised/synthetic data). Change management process governs promotion between environments.
Threat modelling in DevSecOps
Reduce the number of security-related design and coding flaws AND reduce severity of remaining flaws — NOT to reduce number of threat vectors. Apply STRIDE during design. Update threat model when features change. Automate threat modelling in CI/CD pipeline using tools. Security champions in dev teams.
Object-Oriented Programming (OOP) — security concepts
Core OOP concepts
Class: blueprint defining attributes and methods. Object: instance of a class. Method: code defining an action an object performs in response to a message. Message: communication sent to an object to perform an action. Behaviour: results exhibited by object in response to a message. Inheritance: subclass accesses methods of superclass. Polymorphism: objects of different classes responding differently to same message. Encapsulation (data hiding): object hides internal state — only exposes defined interface.
OOP security benefits
Encapsulation limits attack surface — internal state hidden. Supports code reuse — reduces development risk. Natural representation of real-world entities. High cohesion (module works without others) = better security. Low coupling (changes don't cascade) = easier security maintenance. Abstraction = black-box security — users don't need to know internals.
ORBs and middleware
Object Request Brokers (ORBs): middleware that locates and distributes objects across networks. CORBA (Common Object Request Broker Architecture): enables programs in different languages and platforms to communicate via IDL (Interface Definition Language). COM/DCOM (Microsoft): supports object exchange between programs. Security: trust is an issue with distributed systems — mutual authentication required.
Software licensing types
Public domain: anyone can use. Open source: source code available with licence granting rights to study, change, distribute. Freeware: proprietary, no charge but cannot modify/redistribute. Shrink-wrap: licence terms on outside of software packaging (legally binding). Click-through: agreement accepted during installation. Cloud licence: displayed on screen. UCITA = Uniform Computer Information Transactions Act — law against breach of licensing.
Intellectual property in software
Copyright: covers source code and binary — 70 years after author's death. DMCA protects against circumventing copyright protection. Patent: protects inventions including software algorithms — 20 years from filing. Trade secret: proprietary algorithms or designs — protected only by security controls (no registration, no time limit). Trademark: brand names and logos — 10 years renewable.
Covert channels in software
Storage covert channel: one process communicates with another via shared storage. Timing covert channel: one process communicates by modulating resource usage timing. LOKI: tool that creates covert channel by writing data after ICMP header. EAL6 systems have fewer covert channels than EAL3 — covert channels are normally a design flaw. Countermeasure: code review and auditing.
Expert systems & AI concepts
Expert systems
Embody accumulated knowledge of experts on a specific subject. Two main components: Knowledge Base (domain knowledge as IF-THEN rules = forward chaining) and Inference Engine (decision programme that applies knowledge base). Forward chaining: acquires info and reaches conclusion. Backward chaining: backtracks to determine if a hypothesis is correct.
Neural networks
Complex computations that partially replace human mind functions. Based on biological neuron function. Works with weighted inputs — if threshold exceeded, output generated. Single-layer and multi-level architectures. Training period needed to determine input vectors. Adaptability = learning process. Used in anomaly detection and fraud detection in security.
Mobile code security
Java applets: sandboxed — isolated from system resources. No warnings on execution. ActiveX: Microsoft answer to Java applets — authenticode and digital signatures. NOT sandboxed — full access to Windows environment. Annoying dialogs people click away. Local caches: ARP cache poisoning, DNS poisoning, browser cache. CSRF can use cached credentials.
Security in software procurement & third parties
Contracting & procurement security
Any services or applications being onboarded must be reviewed before signing. Ask vendors: What controls protect organisation's information? What sensitive information is stored/processed/transmitted? What security audits does the vendor perform? What access does the client have to those audit reports? Review before onboarding = due diligence.
Software escrow
Source code maintained by a neutral third party. Released to licensee if vendor goes out of business. Protects against vendor business failure disrupting critical systems. Escrow agreement defines trigger conditions for release. Essential for mission-critical commercial software with no open-source alternative.
Open source vs closed source
Open source: source code viewable — more eyes find more bugs — "Linus's Law." Closed source: source code proprietary — can still be reverse-engineered or decompiled. Open system: published APIs allow third-party integration. Closed system: proprietary, no third-party support. Does not define security level — both can be secure or insecure.
