Vulnerability assessment overview
Vulnerability assessments automatically probe systems, applications, and networks looking for weaknesses that may be exploited. ALWAYS get management approval FIRST before any security testing. The purpose is to find weaknesses — not to exploit them (that is penetration testing).
Network discovery scanning
IP probes / IP sweeps / Ping sweeps: automated tools attempt to ping each address in a range — active systems are logged for further analysis. Nmap is the most common tool — identifies port status: Open (application accepting connections), Closed (no application), Filtered (firewall blocking). Default scans miss ~64K ports. First step in reconnaissance — then port scans, then vulnerability scans.
Port scanning techniques
TCP SYN scanning (half-open): sends SYN, if SYN-ACK returned = port open. Requires elevated privileges. TCP Connect scanning: opens full connection — used when no root privileges. TCP ACK scanning: sends ACK flag to probe firewall rules. Xmas scanning: sets FIN, PSH, URG flags — "lit up like a Christmas tree." War dialing: scans phone numbers for modems.
Vulnerability scanning tools
Nessus (Tenable): most popular — combines port scanning with vulnerability detection, checks for known patches. OpenVAS: open-source alternative. Qualys: cloud-based. Core Impact, Nexpose. These tools contain databases of known vulnerabilities and probe targeted systems. Nikto, Burp Suite, Wapiti: web application vulnerability scanners specifically for XSS, SQL injection.
Authenticated vs unauthenticated scans
Unauthenticated: external attacker perspective — finds vulnerabilities visible from outside, misses internal configuration issues. Authenticated: uses read-only credentials to access config files — finds more vulnerabilities including patching gaps, misconfigured services. Authenticated scans are more thorough and preferred for internal assessments.
Passive vs active scanning
Active scanning: sends probe packets to targets — can be detected and may cause disruption. Passive scanning: monitors traffic without sending probes — used in wireless to look for rogue devices. Cannot find all vulnerabilities. IDS/IPS may alert on active scans. Schedule active scans during maintenance windows for critical systems.
Bluetooth scanning
Time-consuming due to many personal devices. Active scan: tests strength of PIN, security mode, pairing configurations. Passive scan: only monitors active connections — must visit same location multiple times to get complete picture. Used to find unauthorized Bluetooth devices in the environment.

CVE, CVSS & NVD
CVE — Common Vulnerabilities and Exposures
Standard convention for identifying and naming vulnerabilities. Maintained by MITRE. Each CVE has a unique identifier (e.g. CVE-2021-44228 = Log4Shell). Provides a common language for discussing vulnerabilities across tools, vendors, and researchers.
CVSS — Common Vulnerability Scoring System
Metrics and calculation tools for: Exploitability, Impact, Maturity of exploit code, and Remediation options. Scores range from 0.0 to 10.0. Critical = 9.0–10.0. High = 7.0–8.9. Medium = 4.0–6.9. Low = 0.1–3.9. Also used to score vulnerabilities against unique organisational requirements.
NVD — National Vulnerability Database
NIST-maintained database of vulnerability information. Contains CVSS scores, remediation guidance, and references for all published CVEs. Free, publicly accessible. Primary reference for vulnerability management programmes. Integrates with Nessus, Qualys, and other scanners.
NSRL — National Software Reference Library
Maintained by NIST. Contains hash values of over 130 million applications. Used in forensics to distinguish known-good software from potentially malicious files. If a file's hash matches NSRL, it is a known application — not malware. Critical for malware analysis and digital forensics.
Penetration testing — knowledge levels
Always obtain WRITTEN management approval before any penetration test. Pen testing without authorisation = illegal. Define scope clearly — what systems are in/out of scope. Document the rules of engagement. Never attempt to "hack back" or avenge a crime.
Zero knowledge
Black box
  • Tester has no prior knowledge
  • Simulates external attacker
  • Most realistic scenario
  • Stealthy — organisation unaware
  • Most time-consuming
Partial knowledge
Grey box
  • Some knowledge of system
  • Acts as a privileged user
  • Can see code, acts as user
  • Balance of realism vs efficiency
  • Common for internal testing
Full knowledge
White box
  • Complete system knowledge
  • Access to source code
  • Acts as a developer
  • Most comprehensive
  • Least expensive — least time
Pen test team types
Blue team
Defensive / internal
Has knowledge of the organisation. Can be done frequently and at least expense. Defenders who know the environment.
Red team
Offensive / external
External and stealthy — simulates real attacker. No prior knowledge. Most realistic. More expensive.
Purple team
Collaborative
Red and blue teams work together in real time. Blue team learns from red team's techniques. Accelerates security improvements.
Penetration testing methodology — phases
1Planning & authorisation — Define scope, rules of engagement, goals. Obtain written management approval. Legal agreements signed. Define what is in/out of scope.
2Reconnaissance / Discovery — Passive (OSINT, Google dorking, LinkedIn, WHOIS) and active information gathering. Footprinting the network. Identify live hosts, open ports, services.
3Enumeration — Port scans, service identification, OS fingerprinting, banner grabbing. Identify user accounts, group memberships, network shares, running services.
4Vulnerability analysis — Map discovered services to known vulnerabilities. Use Nessus, OpenVAS, Nikto. Identify kernel flaws, buffer overflows, misconfigurations, default credentials.
5Exploitation / Attack — Attempt to exploit identified vulnerabilities. Privilege escalation, lateral movement, data exfiltration simulation. Document every action with timestamps.
6Post-exploitation — Assess impact of successful compromise. Maintain access simulation. Identify what an attacker could access. Demonstrate blast radius.
7Reporting — Document all findings, vulnerabilities exploited, evidence. Classify by severity (CVSS). Provide remediation recommendations. Executive summary + technical detail. Egregious holes = report immediately, don't wait.
Pen testing strategies
External testing
Tests from the internet — simulates external attacker. Targets public-facing systems: web servers, email servers, DNS, VPN endpoints. Evaluates perimeter defences. Most commonly requested by management.
Internal testing
Tests from inside the network — simulates insider threat or post-breach attacker. Evaluates internal segmentation, lateral movement potential, privilege escalation paths. Often reveals more critical findings than external testing.
Blind testing
Tester has minimal information. Organisation's security team is aware the test is happening and may actively defend. Tests both offensive techniques and defensive response capabilities simultaneously.
Double-blind testing
Neither the tester nor the organisation's security team knows when or how the test will occur. Most realistic simulation of an actual attack. Tests security team's response without advance preparation. Most controversial — risk of incident response overreaction.
War driving
Driving a vehicle with a laptop/device to find open or weakly secured wireless access points. Used in pen tests to identify rogue APs, weak encryption, and coverage extending beyond facility boundaries. Detect improperly configured guest networks.
Flaw hypotheses methodology
A form of operating system penetration testing. Testers develop hypotheses about flaws based on architecture, design documentation, and code review, then test those specific hypotheses. Systematic — reduces time by targeting likely vulnerabilities first.
Code review & testing types
Code review is the FOUNDATION of software assessment programmes. Earlier defects are found in the SDLC, the cheaper they are to fix. Compiled code poses MORE risk than interpreted code — malicious code can be embedded and is harder to detect.
Static testing (SAST)
Evaluates security WITHOUT running the code. Analyses source code or compiled binary. Requires access to source code. Finds: buffer overflows, injection flaws, hardcoded credentials. Tools: Checkmarx, Veracode, SonarQube.
Dynamic testing (DAST)
Evaluates security IN a runtime environment. Does NOT require source code access. Finds: runtime behaviour issues, XSS, SQL injection in running apps. Tools: Nikto, Burp Suite, OWASP ZAP. More realistic — tests as attacker would.
White-box (crystal)
Detailed exam of logical paths. Checks all possible conditions. Requires access to source code. Tester sees code as a developer. Most thorough — covers all code paths.
Black-box
Observes external system behaviour only. No internal details known. Tester sees the system as an end user. Tests what matters to the end user. Cannot assess internal logic flaws.
Grey-box
Partial knowledge of system internals. Tester has some access — simulates privileged insider or authenticated user. Balances thoroughness with efficiency.
Fuzz testing
Specialised dynamic technique. Provides many different/invalid inputs to stress software and find undetected flaws. Mutation fuzzing: alters existing valid inputs. Generational / intelligent fuzzing: creates inputs from models. zzuf tool automates mutation fuzzing.
Misuse / abuse case testing
Evaluates vulnerability to known risks and adversarial usage. Misuse case diagrams show threats and mitigations. Tests what a malicious user would attempt rather than what a normal user would do.
Regression testing
Verifies that new changes do NOT break previously working functionality. Uses known inputs and compares results to earlier version results. Requires automated process to repeat tests. Nonregression testing = code works as planned.
Interface testing
Assesses performance of modules against interface specifications. Tests APIs, UIs, and physical interfaces. Ensures separately developed modules work together properly. Critical in complex multi-team development.
Formal code review — Fagan inspection
1Planning — Select reviewers, schedule, prepare materials. Define roles: author, moderator, reviewers, recorder.
2
2Overview — Author presents the code/document to reviewers. Team gains understanding of the work product.
3Preparation — Reviewers individually study the code and identify potential defects before the formal inspection meeting.
4Inspection — Formal meeting where reviewers present their findings. Defects are identified, classified, and recorded. No solutions discussed — only defects logged.
5Rework — Author corrects all defects identified during inspection. Creates updated work product.
6Follow-up — Moderator verifies all defects were corrected. Determines if re-inspection is required. Closes the inspection cycle.
Testing levels in SDLC
Unit testing
Tests small individual components (functions, modules) in isolation during development. Done by developers and QA. Ensures quality units are produced for integration. Cheapest and earliest testing level — most cost-effective to find bugs here.
Integration testing
Tests data transfer and control across a program's interfaces. Focused on interactions between pairs of components — does NOT test all functions. Finds bugs in the relationships and handoffs between modules. Important when multiple teams develop different components.
System testing
Demonstrates that all specified functionality exists and that the software product is trustworthy. Tests the complete integrated system against requirements. Includes security testing, performance testing, and user acceptance testing.
Test coverage analysis
Method to assess how well testing covered potential use of an application. Code coverage report includes: functions covered, statements covered, branches covered, conditions covered. Test coverage = tested use cases / total use cases. Higher coverage = more thorough testing.
Synthetic & real user monitoring
Real user monitoring (RUM)
Captures and analyses every transaction of actual users. Provides insight into real-world performance and behaviour. Detects issues only real users encounter. Privacy consideration — captures actual user data.
Synthetic performance monitoring
Uses scripted or recorded data to simulate user transactions. Proactive monitoring — external agents run scripted transactions against a web application. Database monitoring: availability of DB. TCP port monitoring: availability of website/service. Does NOT capture real user sessions.
Log types & sources
Centralised logging assists in maintaining integrity to make evidence legally eligible. Logs taken in the normal course of business are admissible as an exception to the hearsay rule. NTP synchronisation is critical — inconsistent timestamps often caused by improperly set time zones.
Network flow logs
NetFlow (Cisco): captures IP network traffic as it enters/exits an interface. Provides: source/destination of traffic, class of service, causes of congestion, protocol usage. Does NOT capture payload content — only metadata. SPAN port copies all switch traffic to a monitoring device.
Audit logs
Records events on systems for security review. Must contain: transaction date/time, who processed the transaction, at which terminal/system, what action was performed. Critical for accountability — traces actions to subjects. Audit trails are hearsay but admissible when created in normal course of business.
Syslog
Message logging standard commonly used by network devices, Linux/Unix systems, and firewalls. Log levels: Emergency, Alert, Critical, Error, Warning, Notice, Informational, Debug. Event types: Errors (significant problem), Warnings (future problem), Information (successful operations), Success Audits, Failure Audits.
IDS/IPS logs
Intrusion detection and prevention system logs — record detected attacks and suspicious activity. Combined with network flow data, packet captures, and firewall logs to provide complete picture. NIST 800-4: guidelines for IDS/IPS configuration and monitoring. Passive monitoring only works after issues have occurred.
Firewall logs
Record all traffic permitted and denied by firewall rules. Essential for detecting attack patterns, policy violations, and data exfiltration attempts. Should be sent to a centralised SIEM — local storage is insufficient and can be tampered with.
Application logs
Logs generated by applications and web servers. Critical for detecting SQL injection, privilege escalation, authentication failures, and application-layer attacks. Include: login attempts, data access events, errors, and exceptions. Database logs track data access and modification.
SIEM — Security Information & Event Management
What SIEM does
Automates much of the routine work of log review. Provides real-time analysis of events occurring on systems throughout the organisation. Aggregates logs from multiple sources. Correlates events to detect attack patterns. Generates alerts for suspicious activity. Does NOT scan outgoing traffic (that is DLP).
DLP — Data Loss Prevention
Scans data looking for sensitive keywords and patterns. Network-based DLP: placed at edge, scans all outgoing data. Endpoint-based DLP: scans files on a system and files sent to external devices (USB, printers). Will detect and block sensitive data from leaving the organisation. Will NOT modify classification labels in real time.
Protecting logs
Logs must be protected for confidentiality AND integrity. Archival process prevents loss by overwriting. Set maximum log size carefully — if too small, attacker can generate events to push evidence out of the window. Modified logs often indicate intrusion or malicious intent. Send to write-once media or remote SIEM.
Clipping levels
Predefined thresholds for the number of certain error types allowed before the activity is considered suspicious. Example: 5 failed logins = alert. Distinguishes between genuine mistakes and an attack. Companies can set clipping levels as baselines for normal behaviour.
NTP & time synchronisation
NTP (Network Time Protocol): one critical consideration is ensuring logs have accurate timestamps consistent throughout the environment. Set up an internal NTP server synchronised to a trusted public time source. All systems synchronise to the internal NTP server. Without accurate timestamps, log correlation is unreliable and evidence may be inadmissible.
SOC reports — Service Organisation Control
Refer to SOC reports when evaluating cloud vendors. SAS 70 is outdated (replaced in 2011 by ISAE 3402). SOC 1 = financial. SOC 2 = security/operations. SOC 3 = public summary. Type 1 = point in time (design). Type 2 = period of time (design AND operating effectiveness).
SOC 1
Financial reporting controls
  • Internal controls over financial reporting
  • Also known as SSAE 16
  • For financial auditors
  • Relevant for payroll processors, claims processors
  • Type 1 or Type 2 available
SOC 2
Security, availability, integrity, privacy
  • Covers Trust Service Criteria
  • Design and operational effectiveness
  • For business partners and auditors
  • NOT publicly available — restricted
  • Type 1 or Type 2 available
  • Type 2 preferred — shows sustained controls
SOC 3
Public summary report
  • Variation on SOC 2 — same information
  • Presented for a general audience
  • Publicly shareable — website seal
  • Supports organisation's CIA claims
  • Less common than SOC 2
Audit types
Internal audit
Conducted by the organisation's own audit team. Less expensive. May lack independence — familiarity with the environment can bias findings. Useful for frequent reviews and continuous monitoring. Results shared internally. QC = quality control based on internal standards.
External audit
Conducted by a third-party auditor. More objective — no bias from familiarity. Required for regulatory compliance (PCI DSS, HIPAA, SOX). More expensive. QA = quality assurance based on external standards. Results often shared with regulators, partners, and customers.
Third-party audit
External entity audits a supplier or vendor on your behalf. Used in vendor risk management. Example: PCI DSS Qualified Security Assessor (QSA) conducting payment card compliance assessment. Provides assurance about third-party security controls without direct access.
Control assessment (SCA)
Security Control Assessment: formal evaluation of a security infrastructure's individual mechanisms against a baseline of reliability expectations. Generally implemented by federal agencies based on NIST 800-53. Goals: 1. Ensure effectiveness of security mechanisms. 2. Evaluate quality of RM process. 3. Produce report of strengths and weaknesses.
Verification & validation
Verification: objective evidence that design outputs of an SDLC phase meet specified requirements. "Are we building the system right?" May involve third-party verification. Validation: develops level of confidence that software meets all requirements and expectations. "Are we building the right system?" Software improves over time through both V&V cycles.
Deming Cycle (Plan-Do-Check-Act)
Plan: identify opportunity and plan for change. Do: implement change on small scale. Check: use data to analyse results of change. Act: if change successful, implement on wider scale; if fails, begin cycle again. Continuous improvement framework applicable to security programmes.
Security testing considerations — scheduling factors
Factors affecting test scheduling
Availability of testing resources. Criticality of systems protected by the tested controls. Sensitivity of information on tested systems. Likelihood of technical failure of the control. Likelihood of misconfiguration jeopardising security. Risk of system coming under attack. Rate of change of control configuration. Difficulty and time required. Impact on normal business operations.
OPSEC process
Operations Security: understanding your day-to-day operations from the viewpoint of a competitor, enemy, or hacker and then developing and applying countermeasures. Five steps: Identify critical information → Analyse threats → Analyse vulnerabilities → Assess risk → Apply countermeasures.
STRIDE — Microsoft threat modelling framework
STRIDE is used to consider the range of compromise concerns against applications or operating systems. Purpose: reduce the number of security-related design and coding defects and reduce the severity of remaining defects. Can be applied proactively (design/development) or reactively (deployed product).

DREAD — risk rating model
DREAD provides a flexible risk rating solution based on five questions. Each category scored 0–10. Total score / 5 = risk rating. Higher = more dangerous threat. Used to prioritise which threats to address first.

Other threat assessment approaches
Fault tree analysis
Boolean/tree-based analysis of how failures propagate in a system. Starts with an undesired event (top event) and works backward to identify causes. Uses AND/OR gates to model combinations of failures. Used in safety-critical systems and BCP/DRP planning.
Failure Mode & Effects Analysis (FMEA)
Systematic analysis of potential failure modes in a system and their effects. For each component: identify failure mode → determine effects → assess severity → identify causes → assign risk priority number (RPN). Common in hardware and safety engineering — applicable to security systems.
Attack surface analysis
Identifies all points where an attacker could enter or extract data from a system. Attack surface = exposure. Reduce attack surface by: disabling unnecessary services, applying least privilege, removing unused accounts, closing unnecessary ports, minimising code. Smaller attack surface = lower risk.
Threat intelligence
Collecting and analysing information about threats to inform security decisions. Sources: open-source (OSINT), commercial feeds, ISACs (Information Sharing and Analysis Centres), government (CISA, FBI). Indicators of Compromise (IoCs): IP addresses, domain names, file hashes, email addresses associated with attacks.
PASTA — Process for Attack Simulation & Threat Analysis
Seven-stage risk-centric threat modelling framework. Aligns business objectives with technical requirements. Stages: 1. Define objectives, 2. Define technical scope, 3. Application decomposition, 4. Threat analysis, 5. Vulnerability/weakness analysis, 6. Attack modelling, 7. Risk/impact analysis.
Honeypots & honeynets
Honeypot: decoy system designed to attract attackers and study their methods. Pseudo-flaw = false vulnerability in a system to attract an attacker. Enticement: legal — luring an intruder into a honeypot. Entrapment: illegal — inducing a crime the individual had no prior intent to commit. Honeynet: network of honeypots.
Reconnaissance attack types
IP probes / ping sweeps
First type of network reconnaissance against a targeted network. Automated tools ping each address in a range. Active systems are logged for further analysis. Inactive addresses assumed unused. Widespread on the internet — public IP systems receive pings within hours. Strong case for disabling external ping responses.
Port scans
After IP sweep, identifies which services are running on active systems. Scans commonly used ports to find specific service types. Nmap is the most common tool. Port scan tools used in legitimate pen testing AND by attackers. Can be detected by IDS — often triggers security alerts.
Darknet
Unused network space that may detect unauthorised activity. Any traffic to darknet space indicates reconnaissance or misconfiguration — no legitimate systems should be there. Useful for detecting internal network scanning and lateral movement.
Superzapping
Using a system utility or application that bypasses all access controls and audit/logging functions to make updates to code or data. Named after IBM utility. When used by administrators, it bypasses normal change control — requires compensating controls such as peer review and dual control.
