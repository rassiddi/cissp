The four pillars of IAM — I A A A
Identification provides uniqueness · Authentication provides validity · Authorisation provides control · Accountability provides traceability. Identity AND Authentication are both required for Accountability — but NOT necessarily for Authorisation.
Identification
User claims an identity. Unique username, account number, keycard issuance. Binds user to appropriate controls based on unique user instance.
Authentication
Verifying the claimed identity. User provides private data. Establishes trust between user and system for privilege allocation.
Authorisation
Resources the user is allowed to access — defined and monitored. First piece of credentials provides authorisation. DAC / MAC / RBAC / Rule-BAC models.
Accountability
Tracing an action to a subject. Logging is the best way to provide accountability. Includes change log for approved changes and change management processes.
Core concepts — tap to expand
Principle of least privilege
Every subject is granted only the minimum access rights required to perform its function. Applies to users, processes, services, and applications. Includes both permissions (access to objects) and rights (ability to take actions). Regular review and audit of access rights is required.
Need-to-know
Subjects are granted access only to what they need for their work tasks. A subject may have clearance to access data but is not granted authorisation unless they actually need it. Distinct from least privilege — need-to-know addresses information access while least privilege also covers system rights.
Separation of duties
Ensures sensitive functions are split into tasks performed by two or more employees. Creates a system of checks and balances. Prevents fraud, errors, and collusion. No single person should control a complete sensitive process end-to-end. Two-man control requires two people to review and approve. Dual control requires two people to complete a task.
Implicit deny
The basic principle that most authorisation mechanisms use. Access to an object is denied unless access has been explicitly granted to a subject. Default stance is always DENY — access must be affirmatively granted.
Access control matrix
Table that includes subjects, objects, and assigned privileges. When a subject attempts an action, the system checks the matrix. Columns = ACLs (object-focused). Rows = Capability Tables (subject-focused). ACL: which subjects can access this object. Capability table: which objects can this subject access.
Permissions, rights & privileges
Permissions: access granted for an object — what you can do with it (read, write, delete). Rights: ability to take an action on an object (modify system time, restore backup data). Privileges: combination of rights and permissions — full administrator privileges = full rights + full permissions.
Constrained interface
Applications restrict what users can do or see based on privileges. Methods: hide the capability if user lacks permission, show as greyed-out/disabled, or restrict menus entirely. Implements least privilege at the application layer.
Content vs context-dependent controls
Content-dependent: restrict access based on internal data content of each field (e.g. a database view). Context-dependent: require specific activity before granting access (e.g. work-hours restrictions — cannot access system outside business hours).
Authentication factor types
Type 1
Something you know
  • Password
  • PIN
  • Passphrase
  • Cognitive password (mother's maiden name)
  • One-time password (OTP)
Type 2
Something you have
  • Smart card (CAC)
  • Hardware token
  • Memory card
  • USB drive / key
  • OTP token (synchronous / asynchronous)
Type 3
Something you are / do
  • Fingerprint / finger scan
  • Retina scan
  • Iris scan
  • Facial geometry
  • Hand geometry
  • Voice print
  • Signature dynamics (what you do)
  • Keyboard dynamics (what you do)
Type 4
Somewhere you are
  • Location-based (GPS)
  • IP geolocation
  • Network location
  • Cell tower location
MFA (Multi-Factor Authentication) requires two or more factor TYPES. Using two passwords = still single factor (both Type 1). Strong authentication = Type 1 + Type 2 + Type 3 combined. Exam tip: Type 2 error (FAR) is FAR from Type 1 error (FRR).
Passwords (Type 1) — key concepts
Password storage
Passwords are NEVER stored in cleartext in well-designed systems. Salted hashes are stored and compared. Salt (NONCE) = random value added before hashing to prevent rainbow table attacks. On Windows: LM hash and NT Hash. SYSKEY utility encrypts the hashed passwords in their store. PBKDF2 (Password-Based Key Derivation Function 2) is commonly used.
Password attacks
Brute force (exhaustive): tries all possible character combinations. Dictionary attack: tries common words and variations. Rainbow table: pre-computed hash lookup tables — defeated by salting. Social engineering: most effective method. Shoulder surfing. Keystroke logging. Phishing for credentials.
OTP — One-Time Password
Synchronous (time-based): time or counter synchronised between token and server. SecurID is an example. Asynchronous (not time-based): server sends a challenge/nonce, token encrypts it, returns OTP. Challenge/response token: generates response to a system-provided challenge. With added PIN = strong two-factor authentication.
Static token (Type 2)
Owner authenticates to the token, then the token authenticates to the system. Examples: smart cards, proximity cards, USB tokens. Static password token: same password used repeatedly from the token device.
Smart cards
Have an embedded chip to process information. Used for multi-factor authentication. Contains a microprocessor — can perform cryptographic operations. Different from memory cards (which only store, not process). Common Access Card (CAC) = DoD smart card. Side-channel attacks can extract keys from smart cards.
Clipping levels
Predefined thresholds for the number of errors allowed before activity is considered suspicious. Example: 3 failed login attempts before lockout. Clipping level helps distinguish genuine mistakes from an attack. Part of a security monitoring and auditing strategy.
Biometric error rates — the most critical concept
Type 1 Error — FRR
False Rejection Rate
Legitimate user rejected — system too strict. Frustrating for users. Increases with higher security settings.
Type 2 Error — FAR
False Acceptance Rate
Impostor accepted — system too lenient. Security risk. Decreases with higher security settings. Exam tip: Type 2 (FAR) is FAR from Type 1 (FRR).
CER / EER
Crossover Error Rate
Point where FRR = FAR. Lower CER = more accurate system. Used to compare biometric systems. The gold standard metric.
Enrolment time
Max 2 minutes
Enrolment time over 2 minutes is unacceptable. Must occur FIRST before any biometric authentication. Captures the biometric template.
Throughput time
10 people/min
Amount of time taken for a biometric device to scan the subject. Target: 10 people per minute minimum.
Most expensive and most accurate biometric = Retina scan. Most widely used = Fingerprint/finger scan. Most accepted (2nd most accurate) = Iris scan. Retina reveals health conditions (blood pressure, pregnancy) — contains PHI — may not be acceptable in all contexts.
Biometric types — characteristics & accuracy
Retina scan
Scans blood vessel pattern on the back of the eyeball. Most accurate biometric. Reveals health conditions — contains PHI. Requires close proximity.
Most accurate · PHI risk
Iris scan
Scans the coloured portion of the eye surrounding the pupil. Iris is stable throughout life. No sunlight in iris scanner. Most accepted form — second most accurate.
Most accepted · Stable
Fingerprint / finger scan
Fingerprint = stores full print (one-to-many identification). Finger scan = stores only features/minutiae (one-to-one). Most widely used biometric today. Relatively low cost.
Most widely used
Facial scan
Analyses bone structures, nose ridges, eye widths, forehead sizes and chin shapes. Non-intrusive. Can be fooled by photographs. Lower accuracy than iris/retina.
Non-intrusive
Hand geometry
Measures shape, length and width of the hand and fingers. Simple and low-cost. Less accurate than fingerprint. Zephyr chart = iris scan reference.
Low cost
Palm scan
The palm has creases, ridges and grooves unique to a specific person. Appropriate by itself as a Type 3 authenticator. More surface area than fingerprint.
Standalone Type 3
Voice print
Distinguishes differences in speech sounds and patterns. Affected by illness, background noise, aging. Used in phone-based authentication systems.
Behavioural
Signature dynamics
Captures electrical signals of speed, pressure, and time when a person writes a signature. Behavioural biometric — "something you do" (Type 3).
Something you do
Keyboard dynamics
Captures electrical signals when a person types a certain phrase — rhythm, speed, inter-key timing. Behavioural biometric. Can be used as continuous authentication.
Something you do
SSO — Single Sign-On
SSO benefits
Ability to use stronger passwords (only one to remember). Easier administration. Less time to access resources. Reduced password fatigue. Centrally managed credentials.
SSO risks
Single point of compromise — if one credential is stolen, ALL resources can be accessed. If the SSO database is compromised, all passwords are exposed. Requires high availability of the SSO system — it becomes a single point of failure.
Scripted access
Establishes communication links by providing an automated process to transmit logon credentials at the start of a logon session. Basic SSO mechanism — credentials automated via scripts. Less secure than token-based SSO.
SESAME
Secure European System for Application in a Multi-vendor Environment. Implemented to overcome weaknesses of Kerberos. Uses both symmetric AND asymmetric encryption (improvement over Kerberos). Two tickets: one for authentication (like Kerberos), one that defines access privileges (PAC — Privileged Attribute Certificate).
Kerberos — the dominant SSO protocol
Kerberos uses SYMMETRIC key cryptography (AES). Addresses Confidentiality, Integrity, and Authentication — NOT Availability. Based on MIT Project Athena. Now built into Windows (replaced NTLM). 5-minute time synchronisation tolerance — time skew = authentication failure. KDC = single point of failure.
KDC
Key Distribution Centre
Trusted 3rd party. Knows ALL secret keys. Contains Authentication Server (AS) and Ticket Granting Server (TGS). Single point of failure.
AS
Authentication Server
Verifies the authenticity and timeliness of TGTs. Issues the initial TGT after verifying credentials.
TGS
Ticket Granting Server
Issues service tickets when presented with a valid TGT. Subject presents TGT to access each service.
TGT
Ticket Granting Ticket
Proof of KDC authentication. Encrypted, includes symmetric key, expiration time, and user's IP address. Installed by client at login.
Ticket
Service Ticket
Encrypted message proving a subject is authorised to access a specific object/service. Obtained from TGS.
Realm
Auth domain boundary
Authentication administrative domain. Defines the boundaries within which an AS has authority to authenticate users, hosts or services.
Kerberos authentication flow
1User enters credentials — username and password on the client. Client encrypts the username with AES for transmission to the KDC.
2KDC verifies username — checks against credentials database. Generates a symmetric session key encrypted with a hash of the user's password, PLUS an encrypted time-stamped TGT.
3Client receives TGT — installs the TGT for use until it expires. Decrypts the symmetric session key using a hash of the user's password. Passwords are NEVER exchanged — only hashes.
4Client requests service access — presents TGT to the Ticket Granting Server (TGS) to request a service ticket for a specific resource.
5TGS issues service ticket — validates the TGT and issues an encrypted service ticket for the specific resource.
6Client accesses resource — presents service ticket to the target application/server. Access is granted without re-entering credentials.
Directory services
LDAP — Lightweight Directory Access Protocol
Client/server-based directory query protocol loosely based on X.500. Port 389 (unencrypted). LDAPS = Port 636 (over TLS). Manages user information and certificates. X.500 is the hierarchical naming standard. Distinguished Names (DNs) identify objects. Example: cn=rashid+ou=security+dc=cisspmadeeasy+dc=com.
Active Directory
Microsoft's implementation of directory services using LDAP and Kerberos. Group Policy Objects (GPOs) enforce security settings. Sophisticated security resources: group policy, user rights, accounts, DNS services. Domain controllers replicate the directory database. Replaced NTLM with Kerberos authentication.
Meta directory vs virtual directory
Meta directory: gathers information from multiple sources and stores it in ONE central directory — synchronises all sources. Virtual directory: only points to where data resides in multiple sources — does not store a copy, queries original sources in real time.
Federated identity management
Federation = sharing identity and authentication behind the scenes across business boundaries. Example: booking a flight then being offered hotel booking without re-authenticating — both sites are in the same federated domain. SAML is the enterprise standard. OAuth is the commercial/consumer standard.
SAML 2.0
Security Assertion Markup Language. XML-based standard for exchanging authentication and authorisation data between security domains. Best choice for federated identity management. SAML 2.0 enables web-based SSO. Three roles: Principal (user), Identity Provider (IdP), Service Provider (SP). Relies on TLS and digital signatures for security — does NOT have a built-in security mode. If home organisation is offline, implement cloud-based IdP. SAML attack: attacker falsifies SAML communications or steals an access token to bypass authentication.
OAuth 2.0
Open standard for AUTHORISATION (not authentication). Allows a user to grant third-party applications access to their data without sharing passwords. "Delegate access" framework. Exam tip: SAML = enterprise/authentication. OAuth = commercial/authorisation. Windows uses Kerberos for authentication, OAuth for web applications, TACACS+ for network devices, RADIUS for wireless/network access.
OpenID Connect (OIDC)
Built on top of OAuth 2.0 — adds authentication. RESTful, JSON-based protocol. Provides identity verification and basic profile information. OpenID = used for authentication. OAuth = used for authorisation. Together they provide full identity federation for consumer applications. Phishing attack possible by sending fake authentication data.
SPML
Service Provisioning Markup Language. XML-based framework designed for exchanging user information for federated identity single sign-on purposes. Based on Directory Service Markup Language (DSML). Allows platforms to generate and respond to provisioning requests. Used to provision identities across federated domains.
XACML
Extensible Access Control Markup Language. Used to define access control policies within an XML format. Commonly implements RBAC. SAML is for exchanging auth data. XACML is for defining access control policies. SOAP = messaging protocol used to transport XML — NOT a markup language itself.
Shibboleth
Open-source federated identity solution based on SAML 2.0. Widely used in higher education and research organisations. Allows sharing of web resources across organisational boundaries. Implements the InCommon federation for US universities and research institutions.
IDaaS — Identity as a Service
What is IDaaS?
Third-party service providing identity and access management. Effectively provides SSO for cloud environments. Especially useful when internal clients access cloud SaaS applications. Examples: Okta, Azure AD, Ping Identity. Google: login once, access multiple Google products = IDaaS model.
IDaaS capabilities
Provision identities to target applications. User authentication and SSO. Authorisation enforcement. Log events and auditing. Federation — sharing identity across business boundaries. Access Management enforces RULES. Directory synchronisation with on-premises systems.
Cloud identity models
Cloud Identity: users created and managed in the cloud (e.g. Office 365). Directory Synchronisation: users managed on-premises, synced to cloud identity provider. Federated Identity: on-premises IdP handles login requests — used to implement SSO across cloud and on-premises. MS Active Directory + ADFS (Active Directory Federation Services).
SCIM
System for Cross-domain Identity Management. Open standard for automating the exchange of user identity information between identity domains or IT systems. Used to automate provisioning/deprovisioning across cloud services. Enables automatic account creation/deletion when users join or leave.

DAC — Discretionary Access Control
How DAC works
The owner, creator, or data custodian controls and defines access to an object. All objects have owners — access control is based on the owner's discretion. Implemented using ACLs (Access Control Lists) on objects. Each ACL defines types of access granted or denied to subjects. Owner can modify permissions at will — decentralised control.
Identity-based access control
A subset of DAC — systems identify users based on their identity and assign resource ownership to identities. Access control matrix: rows = subjects, columns = objects. Capability tables: subject-focused (what objects can this subject access). ACLs: object-focused (what subjects can access this object).
DAC limitations
No centrally controlled management — owners can alter ACLs at will. Difficult to form a system-wide view of all user access. May result in inconsistent procedures. Easy for access creep to occur if reviews aren't conducted regularly. Trojan horse attacks can exploit DAC — malicious code runs with the owner's privileges.
MAC — Mandatory Access Control
How MAC works
A central authority determines access based on security labels. ALL subjects and objects are labelled. User clearance must be ≥ object classification to access. Government #1 model. Lattice-based. Enforces Bell-LaPadula (confidentiality) or Biba (integrity) models. Non-discretionary — users CANNOT change access controls.
Labels and clearances
Government labels: Top Secret → Grave damage. Secret → Critical damage. Confidential → Serious damage. Unclassified → No damage. Commercial labels: Confidential, Private, Sensitive, Public. "Dominate" in MAC means access to higher or equal access class.
Need-to-know in MAC
Even with MAC clearance, need-to-know still applies. Having Top Secret clearance does NOT automatically grant access to all Top Secret data — the subject must also have a legitimate need to access the specific information. Restriction on top of the label system.
RBAC — Role-Based Access Control
How RBAC works
Access is based on job role or assigned tasks. Often implemented using groups. Form of non-discretionary access control. Most widely used model in commercial environments — #1 used. Administrator assigns roles; roles have permissions; users are assigned to roles. Changes require updating the role, not individual ACLs. Supports separation of duties naturally.
Hybrid RBAC / Limited RBAC
Hybrid RBAC: combines role-based with other access control methods. Limited RBAC: can model all groups within the organisation. RBAC can model: simple (flat), hierarchical (roles inheriting permissions), constrained (separation of duty enforcement), and symmetric RBAC.
Rule-BAC vs RBAC
Rule-BAC: based on rules within an ACL — global rules applied to ALL subjects equally (e.g. firewalls, routers). RBAC: based on job roles — different users have different roles with different access. Key distinction: Rule-BAC has GLOBAL rules affecting everyone. RBAC has role-specific permissions. Both are forms of non-discretionary access control.
Account provisioning & lifecycle management
Provisioning (hire)
Create JD/PD → Job classification → Candidate screening and background check → Standardised interview → Onboarding. Grant IAM account based on Principle of Least Privilege. Employment agreements, NDA, Acceptable Use Policy (AUP). Regular review and audit of Job Description required to ensure access rights remain appropriate.
Entitlement
Amount of privileges granted to users, typically at first account provisioning. Entitlement should be based on job function and least privilege. User entitlement audit can detect when employees have excessive privileges. Privilege creep = aggregation of excess privileges accumulated over time through role changes.
Aggregation (privilege creep)
Users accumulate privileges over time as they move between roles without old privileges being revoked. Prevention: periodic access reviews, quarterly entitlement audits, automated deprovisioning tied to role changes. Separation of duties helps prevent privilege aggregation from creating single points of compromise.
Account review
Periodic review of all user accounts and their access rights. Should include: active accounts with no recent login, accounts with excessive privileges, service accounts, shared accounts. Part of ongoing security monitoring. Regular recertification ensures least privilege is maintained over time.
Deprovisioning (offboarding)
FIRST: disable the account. THEN: delete it after an appropriate interval (for audit trail preservation). Conduct exit interview. Collect all company assets — laptop, keys, access cards, tokens. Remind departing employee of NDA obligations. Never delete immediately — may need forensic access later.
Transfers & role changes
When an employee changes roles, old access rights should be revoked promptly and new rights assigned. Failure to revoke old access = privilege creep. Should trigger a formal re-provisioning process. Manager certification of access rights at each role change is best practice.
Special account types — risks & controls
Privileged accounts
Administrator, root, and other high-privilege accounts. Highest risk accounts — must be tightly controlled. Controls: separate privileged account from daily-use account, use PAM (Privileged Access Management) tools, log all privileged actions, enforce MFA, time-limited privilege escalation, just-in-time access.
Service accounts
Accounts used by applications and services — not human users. Often have excessive privileges and never expire. Controls: assign minimum necessary privileges, use managed service accounts, rotate passwords regularly, log all activity, never use domain admin for service accounts.
Shared accounts
Multiple users sharing a single account — destroys accountability. Cannot trace actions to a specific individual. Should be avoided whenever possible. If unavoidable: strict logging, physical controls, periodic password rotation with documented access requests. Most legacy systems require this — migration plan needed.
Guest / anonymous accounts
Default accounts with minimal privileges for unauthenticated access. Should be disabled if not actively needed. When required: strict network segmentation, minimal permissions, extensive logging. Common attack vector — default guest accounts often have weak/no passwords.
Centralised vs decentralised IAM
Centralised
Single control point
Very strict control. Only modified through central administration. Examples: Kerberos, RADIUS, TACACS+, SSO. Consistent policies. Single point of failure risk.
Decentralised
Owners control access
Access controlled by owners/creators of information. May lack consistency. Difficult to form system-wide view. Scales better for large organisations with varied needs.
Hybrid
Mixed approach
Centralised for critical/sensitive systems, decentralised for others. Most enterprise environments use this approach. Balances control with flexibility.
Callback
Remote access control
System calls back to a predetermined number after initial dial-in. Authenticates the location, not just the user. Less useful for travelling workers.
